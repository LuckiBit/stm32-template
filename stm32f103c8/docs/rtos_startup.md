# Application RTOS 启动架构

本模板采用“编译期选择任务与资源，调度后协调就绪，再放行业务”的方式。
本文路径以 `application/` 为基准；五层结构和 Bootloader 流程见 [系统架构](firmware_arch.md)。

## 文件职责

| 位置 | 职责 |
| --- | --- |
| `app/tasks/tasks.h` | 任务与资源的编译期开关、默认依赖和配置合法性检查 |
| `core/FreeRTOSConfig.h` | 内核配置；根据软件定时器开关决定是否创建定时器服务任务 |
| `core/system_init.c` | HAL、时钟、GPIO、已启用串口基础初始化 |
| `core/rtos_start.c` | 创建管理模块与已启用业务资源，启动调度器 |
| `app/system_manager` | 常驻管理任务、就绪截止时间、统一放行、故障接收 |
| `app/tasks` | 16 个编号任务槽位及配套资源；只为启用项提供静态存储 |
| `app/led`、`service/led` | LED 状态机与 LED 服务 |
| `core/rtos_fault.c` | 保存首个故障码，调用 BSP 后停机 |
| `hardware/bsp/gpio` | 板级 GPIO 初始化、LED 输出及故障输出处理 |
| `hardware/bsp/uart` | 5 路独立串口配置、按需初始化和带超时的轮询发送接口 |

管理模块通过入口注入的 `tasks_start` 回调启动业务服务，不直接包含 `tasks.h`。
业务任务通过管理模块的就绪和许可接口参与启动。
任务开关与接口统一放在 `tasks.h`，该头文件仅依赖 C 标准头文件；创建和启动接口使用
`bool` 返回成功或失败，允许 `FreeRTOSConfig.h` 读取开关而不产生循环包含。

## 默认配置与任务数量

默认只启用 `task_4`，即 LED 业务。启动后共 **3 个任务**：

| 任务名 | 优先级 | 栈深度（字） | 默认行为 |
| --- | ---: | ---: | --- |
| `task_4` | 5 | 128 | 等待启动许可后调用 `led_run()` |
| `system` | 5 | 256 | 等待已启用任务就绪，运行后阻塞等待故障 |
| `IDLE` | 0 | 128 | FreeRTOS 内核空闲处理 |

一字为一个 `StackType_t`，当前 Cortex-M3 上为 4 字节；RTOS tick 为 1000 Hz。
优先级范围为 0～6，数值越大优先级越高。任务编号不决定优先级。

`task_0`～`task_15` 是可选的代码槽位，不是默认全部创建的 16 个任务。
实际总数为 **启用的业务任务数 + 1 个管理任务 + 1 个空闲任务 + 可选的定时器服务任务**。
启用全部 16 个业务任务时，默认依赖会启用定时器服务，任务总数为 19。
全部业务任务关闭时，只有管理任务和空闲任务，管理器不等待业务就绪位。

## 编译期开关

所有开关集中在 [`tasks.h`](../application/app/tasks/tasks.h)，只允许取值 `0` 或 `1`。
默认值使用 `#ifndef`，也可通过编译参数覆盖；同一配置必须一致地应用于所有源文件。

| 开关 | 可配置范围 | 默认设置 |
| --- | --- | --- |
| `TASK_ENABLE_n` | 0～15 | 只有 `TASK_ENABLE_4=1` |
| `QUEUE_ENABLE_n` | 0～7 | 全部为 0 |
| `SEMAPHORE_ENABLE_n` | 0～7 | 全部为 0 |
| `MUTEX_ENABLE_n` | 0～7 | 全部为 0 |
| `TIMER_ENABLE_n` | 0～3 | 0、1 默认跟随对应任务；2、3 默认为 0 |
| `EVENT_GROUP_ENABLE_n` | 0～3 | 0、1 默认跟随对应任务或定时器；2、3 默认为 0 |

例如，启用编号 15 的预留任务，将其默认值改为：

```c
#ifndef TASK_ENABLE_15
#define TASK_ENABLE_15 1
#endif
```

重新构建后，管理器会自动将任务 15 纳入就绪集合。它的入口目前在放行后阻塞等待通知，
需要在该槽位中实现业务。启用开关本身不会生成业务行为。

禁用任务时，其函数、声明、句柄、栈和控制块均通过条件编译排除。
禁用资源时，其缓冲区、句柄、创建与检查代码也一起排除，不依赖链接器优化来节省空间。
队列、信号量、互斥量不自动跟随相同编号的任务，因为它们可能被多个任务共享；
接入具体业务时按实际依赖启用。

### 依赖与配置错误

- 当前 `task_0` 依赖定时器 0 和事件组 0，`task_1` 依赖定时器 1 和事件组 1。
- 启用这两个任务时，默认开关自动启用对应定时器和事件组。
- 如果显式关闭当前任务必需的定时器，或关闭任务/回调依赖的事件组，预处理阶段报错。
- 将开关设置为 0、1 之外的值同样报错。
- 所有软件定时器关闭时，`configUSE_TIMERS=0`，不创建内核定时器服务任务及命令队列。
- 任一软件定时器开启时，恢复 `Tmr Svc`（优先级 6、栈深度 256 字）。
  它处理所有已启用定时器的回调，不为每个定时器单独创建任务。

当前内核的 `INCLUDE_xTimerPendFunctionCall` 同样跟随定时器服务开关。
后续如使用依赖该服务的功能（例如事件组的 ISR 延迟操作），需一并审视内核配置。

## 资源槽位与启用后的行为

| 对象 | 槽位数量 | 默认创建数 | 启用后的初始行为 |
| --- | ---: | ---: | --- |
| 业务任务 | 16 | 1 | 完成本地初始化、报告就绪、等待运行许可 |
| 消息队列 | 8 | 0 | 每个默认容纳 5 个 `uint32_t`，初始为空 |
| 二值信号量 | 8 | 0 | 初始不可获取 |
| 互斥量 | 8 | 0 | 初始可获取 |
| 业务事件组 | 4 | 0 | 初始事件位为零 |
| 软件定时器 | 4 | 0 | 创建后由启动回调启动 |

管理器自己的事件组始终存在，不计入 4 个业务事件组槽位。
内核定时器命令队列只在定时器服务开启时存在，不计入 8 个业务队列槽位。

| 业务任务槽位 | 优先级 | 栈深度（字） | 启用并放行后的行为 |
| --- | ---: | ---: | --- |
| `task_0` | 1 | 128 | 等待事件组 0；定时器 0 每 500 ms 设置事件位 |
| `task_1` | 2 | 128 | 等待事件组 1；定时器 1 每 1000 ms 设置事件位 |
| `task_2` | 3 | 128 | 阻塞等待通知，业务预留 |
| `task_3` | 4 | 128 | 阻塞等待通知，业务预留 |
| `task_4` | 5 | 128 | 执行 LED 状态机 |
| `task_5`～`task_15` | 1 | 128 | 阻塞等待通知，业务预留 |

软件定时器 2、3 默认关闭；手动启用后也会启动，但当前回调没有业务内容。
所有定时器回调中的后续实现必须保持非阻塞。

已启用但暂时没有工作的任务应阻塞等待事件或通知；它仍保留栈和控制块。
这些编译期开关不能在运行中切换。运行期工作模式应在任务业务状态机内实现，
当前模板没有提供统一的业务暂停/恢复接口，也不通过反复创建、删除任务切换模式。

## 启动协议

```text
system_init()
    ↓
system_manager_create(tasks_start, REQUIRED_TASKS)
    ↓
tasks_create()：仅创建启用的资源和任务
    ↓
vTaskStartScheduler()
    ↓
system：INITIALIZING
    ├─ 已启用任务完成本地初始化，报告就绪并等待许可
    └─ 管理器只等待 REQUIRED_TASKS 中的位，最长 5000 ms
    ↓
tasks_start()：启动已启用的软件定时器；没有定时器则直接成功
    ↓
system：RUNNING，置位运行许可
    ↓
业务任务执行；管理任务常驻等待故障
```

`tasks.h` 根据 `TASK_ENABLE_n` 计算 `REQUIRED_TASKS`，无需手动维护启用集合。
16 个任务槽位使用位 0～15；管理器用位 16 表示运行许可、位 17 表示故障，
编译期检查确保控制位与允许的就绪位不重叠。必要任务集合为空时直接进入服务启动阶段。

`system_manager_wait_running()` 是一次性启动屏障，不清除许可位，不能用于运行期暂停。
管理器通过通知唤醒并检查持久事件位，分批报告不会重新开始计时。
5 秒只限制管理器等待就绪的阶段，不覆盖调度前初始化，也无法制止死循环或长时间关中断。

`xTimerStart()` 成功表示命令已经入队，不代表回调已执行。
发布 RUNNING 时短暂挂起调度，避免任务上下文故障夹在最终检查与放行之间；该区域不阻塞。
如果初始化需要通信或存储工作线程，必须先让相应服务运行，避免它也等待最终业务许可而死锁。

## 内存策略

固定 RTOS 对象全部使用静态分配；关闭的槽位不分配 RTOS 存储。
内核为实际需要的空闲任务和定时器任务提供静态存储；构建不链接 `heap_4.c`。
这不代表 C 库或未来第三方组件不会使用堆，链接脚本仍为 C 堆和主栈保留最小空间。

任务栈深度和队列容量仍需按真实业务负载核算，不能把预留任务的 128 字栈直接用于复杂协议。

## 故障与状态接口

`system_manager_get_state()` 返回 BOOT、INITIALIZING、RUNNING 或 FAULT 的诊断快照。
创建接口在调度前调用；就绪报告、许可等待、故障报告仅在创建成功后的任务上下文调用。
状态查询可在创建前返回 BOOT，但不能代替启动屏障。

| 故障码 | 触发条件 |
| --- | --- |
| `RTOS_FAULT_MANAGER_CREATE` | 管理器参数无效或资源创建失败 |
| `RTOS_FAULT_APPLICATION_CREATE` | 已启用业务资源或任务创建失败 |
| `RTOS_FAULT_SCHEDULER_RETURN` | 调度器启动后意外返回 |
| `RTOS_FAULT_STARTUP_TIMEOUT` | 已启用任务未在截止时间内全部报告就绪 |
| `RTOS_FAULT_SERVICE_START` | 启动回调失败，当前为启用定时器的启动失败 |
| `RTOS_FAULT_RUNTIME` | 管理器收到故障报告，启动期间同样处理 |
| `RTOS_FAULT_STACK_OVERFLOW` | 内核调用栈溢出钩子 |
| `RTOS_FAULT_ASSERT` | 内核或应用 `configASSERT` 失败 |

`rtos_fault_stop()` 保存首个 `g_rtos_fault`，屏蔽可屏蔽中断、关闭 LED 并停机。
记录不跨复位保留；处理不依赖调度器、日志队列或堆。
紧急硬件危险必须先在本地采取板级措施，再通知管理任务。
新增执行器后，应根据实际电路扩展 `bsp_gpio_safe_state()`。

当前没有看门狗、心跳监测、自动恢复或故障持久化；就绪位也不能证明运行期健康。
HardFault、时钟初始化错误等入口仍走原有路径，不由管理任务接管。

## 验证与配置切换

修改 `app/tasks/tasks.h` 后按 README 的方式重新构建 Application。
使用编译参数覆盖开关时，需要重新配置 CMake，确保构建和编译数据库同步。

验证默认配置时应只有 `task_4`、`system`、`IDLE` 三个任务；启用 0、1 后应新增两个事件任务
及一个定时器服务任务，且两个定时器正常产生事件。
启用高编号任务时需确认其就绪位被等待；全部业务关闭时应正常进入 RUNNING。
故意不报告某个已启用任务的就绪位应导致启动超时；关闭的任务不应造成超时。

构建和 ELF 符号检查可确认条件编译与存储裁剪，实际调度、栈余量及故障输出行为仍需板上验证。
