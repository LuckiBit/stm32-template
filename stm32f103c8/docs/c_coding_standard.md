# C 语言编码规范

## 1 基本要求

- 项目必须明确 C 语言标准、目标平台、编译器和告警级别。
- 代码应兼顾可读性、可维护性、可扩展性、兼容性和可移植性。

### 1.1 当前项目约定

- 两个固件工程均使用 C11、`arm-none-eabi-gcc`，目标为 STM32F103C8T6，启用 `-Wall -Wextra`。
- 源码固定在 `app`、`core`、`hardware`、`service`、`middleware` 五层内组织。
  构建工具、生成目录和文档不属于新的源码层；不另设测试源码层。
- 当前实现与预留能力以 [系统架构](firmware_arch.md) 为准；修改模块时同步更新构建列表和文档。
- 按项目明确约定，`application/app/tasks` 的预留资源采用从 `_0` 开始的连续数字后缀，
  例如 `task_0`、`s_queue_handle_0`、`TASK_NAME_0`。这是第 3 章语义命名规则的局部例外，
  用于稳定标识预留槽位；名称不加演示前缀。其他模块继续使用表达职责的名称。
- 格式由两个工程现有的 `.clang-format` 决定，不修改配置以适配新增代码。
  对齐和续行的具体排版遵循原配置；本节约定优先于后文通用排版描述。
- RTOS 对象使用 `app/tasks/tasks.h` 的编译期开关按需静态分配，关闭项不创建、不保留存储。
  验证按改动范围执行编译、静态检查和板上检查，
  不通过增加新的源码层来组织验证文件。

## 2 代码组织

- 模块应职责单一，并提供最小、清晰的对外接口。
- 头文件声明公共接口、类型和常量，且必须能独立包含。
- 对外可见的全局对象应在 `.h` 文件中使用 `extern` 声明，并在 `.c` 文件中进行唯一的实体定义。
- 内部符号应放在源文件中，并使用 `static` 限制可见性。
- 所有 `.h` 文件必须使用 Include Guard，宏名应与文件名对应，并使用大写字母和下划线。
- 避免可变全局状态、循环依赖和不必要的传递包含。
- 平台相关代码应集中封装，与业务逻辑隔离。

### 2.1 `.h` 文件组织顺序

1. 文件头注释
2. Include Guard
3. `#include`
4. 公共宏定义
5. 公共类型定义
   - `typedef`
   - `enum`
   - `struct`
   - `union`
6. 外部变量声明（`extern`）
7. 公共函数声明
8. `#endif`

### 2.2 `.c` 文件组织顺序

1. 文件头注释
2. `#include`
3. 私有宏定义
4. 私有类型定义
   - `typedef`
   - `enum`
   - `struct`
   - `union`
5. 全局变量定义
6. 私有全局变量
7. 私有函数声明
8. 公共函数定义
9. 私有函数定义

### 2.3 变量声明顺序

变量声明应依次按照声明类别、基础类型和对象形式排序。上一级排序优先于下一级；
不适用的类别应跳过，不得为满足排序规则而改变变量的类型、限定符或存储类别。

#### 2.3.1 声明类别

| 顺序 | 声明类别 |
| -- | -- |
| 1 | `extern` 声明，仅用于头文件 |
| 2 | `static const` 变量 |
| 3 | `static const volatile` 变量 |
| 4 | `static volatile` 变量 |
| 5 | `static` 普通变量 |
| 6 | `static` 数组或缓冲区 |
| 7 | `static` 结构体对象 |
| 8 | `static` 指针 |
| 9 | `static` 函数指针 |

同时符合多个类别时，采用序号最小的类别；第 5 至第 9 类仅用于不含 `const` 或
`volatile` 限定符的 `static` 变量。

#### 2.3.2 基础类型

同一声明类别内部按照以下顺序排列：

1. `bool`
2. `char`
3. `int8_t`、`uint8_t`
4. `int16_t`、`uint16_t`
5. `int32_t`、`uint32_t`
6. `int64_t`、`uint64_t`
7. `enum`、`typedef` 类型
8. `struct` 类型
9. 指针类型
10. 函数指针类型

同一位宽的有符号类型排在无符号类型之前。

#### 2.3.3 对象形式

同一基础类型内部按照以下顺序排列：

1. 单变量
2. 数组
3. 结构体对象
4. 指针

当声明属于数组、结构体对象、指针或函数指针等专门的声明类别时，应优先按照
2.3.1 节排序，再在该类别内部按照基础类型和对象形式排序。

## 3 命名

本章命名规则主要适用于自行编写的文件、类型、变量、函数及其他代码元素。
公共库、第三方库、平台 SDK、公共文件以及其他既有公共接口不受本章约束，
使用时应保留并遵循其原有命名，以保证一致性和兼容性。

### 3.1 命名语义结构

各类名称应遵循“名称本身能够表达语义”的原则：

| 名称类别 | 语义结构 |
| -- | -- |
| 文件 | 模块 + 职责 |
| 函数 | 谁 + 做什么 + 对谁做 |
| 变量 | 谁的 + 什么东西 / 什么状态 |
| 类型 | 模块/对象 + 数据类型 |

其中：

- “模块”表示功能模块、设备模块或功能域；
- “谁”表示执行动作的模块或对象；
- “做什么”表示动作或操作；
- “对谁做”表示操作的目标对象，可根据语义需要省略；
- “职责”表示文件承担的主要功能；
- 变量重点表达所属对象以及所表示的数据、属性或状态。

### 3.2 命名格式

- 名称应准确表达用途，避免含糊缩写、拼音和无语义编号。
- `.c` 文件、`.h` 文件和文件夹名称使用 `snake_case`。
- 结构体、枚举和联合体类型使用 `snake_case`，并以 `_t` 结尾。
- 变量使用 `snake_case`。
- 全局变量以 `g_` 开头，静态变量以 `s_` 开头。
- 常量、宏和枚举成员使用 `SCREAMING_SNAKE_CASE`。
- 函数使用 `snake_case`。
- 布尔值名称应体现判断语义。
- 作用域越大，名称应越完整；短名称仅用于含义明确的局部上下文。

## 4 格式

- 文件统一使用 UTF-8 编码和项目约定的行尾格式。
- 函数体、分支、循环体和其他代码块必须使用大括号，并采用 Allman 风格独占一行；
  不得将短函数或短代码块压缩为单行。
- 使用 4 个空格缩进，不使用制表符；续行同样缩进 4 个空格。
- 每行不得超过 100 个字符；换行后保持层级清晰。
- 二元运算符两侧保留空格。
- 一元运算符与操作数之间不得留空格。
- 三元运算符 `?` 和 `:` 两侧必须保留空格；表达式换行时，必须在 `?` 和 `:` 前换行。
- `(`、`)`、`[`、`]` 与其内部内容之间不得留空格。
- 同一行内，逗号与其后的参数或元素之间必须保留一个空格；逗号位于行末时不得留空格。
- 小型数组允许单行书写。
- 成员访问运算符 `.` 和 `->` 两侧不得留空格。
- 函数名或控制关键字与左括号之间不留空格。
- 指针符号 `*` 紧靠变量名，与类型名之间保留空格。
- `typedef` 定义中，`}` 与类型名之间保留一个空格，类型名后紧跟 `;`。
- `if`、`else if` 和 `else` 必须分别另起一行，不与其他语句同行。
- 一行只声明一个变量，并尽量在声明时初始化。
- 函数声明、定义和调用采用一致的换行方式；未超过行宽时保持单行，换行时每行仅
  放置一个参数，不得将全部参数合并到同一续行。
- `case` 相对 `switch` 缩进一级，分支代码再缩进一级。
- `switch` 分支必须明确终止；贯穿执行时必须注明意图。

## 5 类型、常量与宏

- 类型应匹配数据语义和取值范围；需要确定位宽时使用 `<stdint.h>` 中的类型。
- 有限状态或选项优先使用枚举，相关数据使用结构体组织。
- 使用具名常量替代魔法数字；具有类型语义的常量优先使用 `const` 对象或枚举。
- 函数式宏必须为参数和结果添加括号，并避免参数重复求值；能用函数实现时，优先使用普通函数或 `static inline` 函数。

## 6 函数与控制流

- 函数应职责单一，输入、输出和副作用应明确。
- 参数过多时，应考虑拆分职责或使用结构体组织数据，但不得借此隐藏依赖。
- 使用提前返回或提取函数减少嵌套。
- 表达式应遵循“计算、赋值给具名变量、使用变量”的顺序。
- `if`、`else if`、`while`、`for` 和 `switch` 的控制表达式中不得直接进行二元运算；
  运算结果必须先赋值给具名变量。
- `return` 后不得直接进行二元运算；运算结果必须先赋值给具名变量再返回。
- 函数实参中不得直接进行二元运算；运算结果必须先赋值给具名变量再传入。
- 无副作用的一元运算可以直接用于控制表达式、返回表达式和函数实参。
- 自增运算符 `++` 和自减运算符 `--` 不得用于控制表达式、返回表达式或函数实参，
  必须独立成语句。
- 复杂表达式应拆分，避免混合赋值、状态变更和多重判断。
- 返回值语义必须稳定；调用方必须处理不可忽略的失败结果。
- 公共接口应说明参数约束、返回值、资源所有权、线程安全性和副作用。

## 7 指针与资源

- 指针和长度应成对传递，访问数组或缓冲区前必须检查边界。
- 接口必须明确空指针是否合法，并在适当边界进行校验。
- 指针应在声明时初始化；释放资源后不得继续使用原指针。
- 接口必须明确资源的创建、释放和所有权转移规则。
- 动态内存分配后必须检查结果，并确保所有退出路径正确释放资源。
- 嵌入式或实时系统应明确动态分配策略和失败处理方式。

## 8 错误处理

- 所有可能失败的操作都必须处理结果，不得无理由忽略返回值。
- 同一模块应采用统一的错误表达方式。
- 错误信息应包含必要上下文，但不得泄露敏感数据。
- 清理逻辑必须覆盖部分初始化和中途失败场景。
- 必须防范越界、整数溢出、除零、无效移位、未初始化读取和空指针解引用。

## 9 注释与文档

- 注释应解释意图、约束和原因，不得复述代码。
- 行尾注释与代码之间至少保留两个空格；连续多行的行尾注释应对齐。
- `//` 后必须保留一个空格。
- `/*` 后和 `*/` 前必须各保留一个空格。
- 块注释必须使用 Doxygen 格式。
- 公共接口、关键算法、非直观逻辑以及硬件和协议约束必须有说明。
- `TODO`、`FIXME` 等标记应包含任务编号或责任信息。
- 修改代码时必须同步更新相关注释和文档。

## 10 可移植性、性能与质量

- 代码必须通过所有受支持编译器和平台的验证。
- 不得假设整数位宽、字节序、结构体填充或 `char` 的符号性；确需依赖时必须显式检查或封装。
- 性能优化必须基于测量结果，并记录关键假设。
- 项目应启用严格的编译器告警，并使用格式化、静态分析和自动化测试工具。
- 代码评审应重点检查正确性、接口契约、资源所有权、错误路径、并发安全和可测试性。
- 新增或修复行为时应补充相应测试，缺陷修复应尽量包含回归测试。
- 规范变更应记录原因、适用范围和迁移方式。

## 附录 A 术语说明

### A.1 Allman

一种大括号排版风格，要求左大括号和右大括号分别独占一行，并与对应语句保持一致的缩进层级。

### A.2 Include Guard

一种防止头文件被重复包含的预处理机制。保护宏应与文件名对应，使用格式如下：

```c
#ifndef FILE_NAME_H
#define FILE_NAME_H

/* 头文件内容 */

#endif /* FILE_NAME_H */
```

### A.3 SCREAMING_SNAKE_CASE

一种命名格式，所有字母均大写，单词之间使用下划线分隔。

### A.4 snake_case

一种命名格式，所有字母均小写，单词之间使用下划线分隔。

### A.5 二元运算符

需要两个操作数的运算符：

| 类别 | 运算符 |
| -- | -- |
| 乘除与取模 | `*`、`/`、`%` |
| 加减 | `+`、`-` |
| 移位 | `<<`、`>>` |
| 关系 | `<`、`<=`、`>`、`>=` |
| 相等性 | `==`、`!=` |
| 按位与 | `&` |
| 按位异或 | `^` |
| 按位或 | `\|` |
| 逻辑与 | `&&` |
| 逻辑或 | `\|\|` |
| 赋值 | `=`、`*=`、`/=`、`%=`、`+=`、`-=`、`<<=`、`>>=`、`&=`、`^=`、`\|=` |
| 逗号 | `,` |

数组下标 `[]`、函数调用 `()`、成员访问 `.` 和 `->` 属于后缀运算符，不归入二元运算符。

### A.6 三元运算符

三元运算符又称条件运算符，是 C 语言中唯一需要三个操作数的运算符，格式如下：

```c
condition ? expression_true : expression_false
```

当 `condition` 为真时计算并返回 `expression_true`，否则计算并返回 `expression_false`；
两个结果表达式中仅有一个会被计算。

### A.7 一元运算符

作用于单个操作数的运算符：

| 类别 | 运算符 |
| -- | -- |
| 后缀自增、自减 | `++`、`--` |
| 前缀自增、自减 | `++`、`--` |
| 取地址 | `&` |
| 解引用 | `*` |
| 一元正号、负号 | `+`、`-` |
| 按位取反 | `~` |
| 逻辑非 | `!` |
| 对象或类型大小 | `sizeof` |
| 类型对齐要求 | `_Alignof` |

`_Alignof` 自 C11 起可用，且仅作用于类型名。类型转换 `(type)` 不归入一元运算符。
